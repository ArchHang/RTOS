## 0. 勘误与修订(2026-09-16 优化迭代后追加)

> 本节由后续的性能优化迭代(见 `.trae/scenario_test/OPT_LOG.md`)补充。
> **动手优化前先重跑回归, 发现原测试存在 2 个内核缺陷与 3 处测量口径问题**,
> 因此本报告 §2/§3 的部分结论**已作废或需重新表述**。请以本节为准。

### 0.1 前置修正: 原报告的数据是在带缺陷的内核上采集的

优化迭代开始前, `selftest` 全量回归实测为 **5 FAIL**(而更早的报告声称 0 FAIL)。
其中 2 项是**真实内核缺陷**:

| 缺陷 | 后果 |
|---|---|
| 启动前注册的互斥锁指向**栈对象**, 出作用域后注册表留下悬空指针 | 被动数据损坏源 |
| 测试夹具泄漏互斥锁注册表槽位 → 后续 `mutex_init` 返回 `ERR_NO_MEM` | 该锁**完全失去优先级继承**, 高优先级等待者被确定性饿死 — 表现为静默优先级反转 |

修复后回归达到 **`pass=391 fail=0 info=11 total=402`**。
后续所有对比数据都在这套**已修复的内核**上重采。

### 0.2 作废结论一: S3 的"控制环偏差"

**原文**(§3.3): "控制环偏差: FreeRTOS 0/0, 自研 380199/671818 cyc —— FreeRTOS 完胜"

**问题**: 该指标定义为 `now − (上次唤醒 + 标称周期)`。一旦某次唤醒被推迟超过一个
周期(实测最大间隔 9ms), `expect_cycle` 基准就**永久错过**, 偏差被累积成常数偏移。

**实测证据**(给 S3 补上与 S4 同口径的"实际唤醒间隔"测量):

```
control_period_cyc:    N=600 avg=840279 min=335943 max=1511653
control_deviation_cyc: N=599 avg=381660 min=5      max=674793
```

`840279 周期 = 5.002 ms`, 而 `S3_CONTROL_PERIOD_MS` **就是 5** —— **实际周期是正确的**。
381660 ≈ 半个周期, 是累积基准漂移, 不是真实抖动。

⇒ **该结论作废**。重负载下的周期对比必须改用 `control_period_cyc`(实际唤醒间隔)
重新在两侧采集。

### 0.3 作废结论二: S2 的 "give 慢 2.04×/2.20×/2.42×"

**原文**(§3.2): "自研 give 967/1045/1145 vs FreeRTOS 474/474/474, 慢 2.04×~2.42×"

**问题**: `give_w*` 测的是**"调用 give 到返回"的墙钟时间**, 而这段时间里任务**可能被
换出**(被唤醒者要与调用者交替运行)。新增"整回合(give + `delay(1)`)"测量后真相明确:

| 指标 | 自研 | FreeRTOS | 判定 |
|---|---|---|---|
| **`give_no_waiter`(纯固定开销, 无唤醒无切换)** | **91** | 187 | **自研快 2.05×** ✅ |
| `give_w01`(端到端墙钟) | 1045 | 474 | 含换出等待, 口径不纯 |
| **`round_w01`(整回合 = give + delay1)** | **166823** | **167404** | **持平(自研略快 0.35%)** |
| give 占整回合比例 | 0.63% | 0.28% | — |

整回合 ≈ 166823 周期 ≈ **1ms**, 即整回合就是那一次 `delay(1)` ——
**两个内核的 tick 精度与每毫秒调度开销实质相同**。

⇒ **"give 慢 2.2×"必须重新表述为**: 自研的 **give 纯固定开销优于 FreeRTOS**
(91 vs 187); 原比值是"含被换出等待的端到端墙钟口径", 不能解读为 IPC 执行成本。

### 0.4 仍成立的核心结论: 等待链 O(n) 退化(已修复)

**原文**(§3.2): "自研 give 成本随阻塞等待者数线性增长(+18.4% @8), FreeRTOS 恒定"

**该结论成立, 且已据此优化**: 等待链从"按优先级有序插入 O(n)"改成
"尾插 + 优先级位图(`__builtin_ctz` 选最高优先级)"。

| 等待者数 | 优化前 | 优化后 |
|---|---|---|
| 1 / 4 / 8 | 967 / 1045 / 1145 | 1038 / 1064 / **1088** |
| **退化量(1→8)** | **+18.4%** | **+4.8%** |
| **每等待者增量** | **~25 cyc** | **~7 cyc** |

伸缩性退化**缩小 74%**。回归 `fail=0`(其中 `test_sem_priority_wake` 与
`FIXP2 waitlist_requeued` 两个直接验证唤醒序的用例通过, 是等价性的关键证据)。

### 0.8 新增: give 路径分段计时 —— 残余差距的精确定位

把 `rtos_sem_give` 拆成三段分别用 DWT 累加(S2 场景, 自研, 每段均值):

| 段 | w01 | w04 | w08 | 占比 |
|---|---|---|---|---|
| 进入临界区 | 33 | 33 | 33 | 2.8% |
| 唤醒 + 解除阻塞 + 抢占判定 | 296 | 299 | 299 | 25% |
| **退出临界区(含抢占切换窗口)** | **665** | **693** | **717** | **59%** |

**两条结论**:

1. **唤醒路径已不是瓶颈** —— `seg_wake` 296-299 周期, 与 FreeRTOS 的
   `give_no_waiter` 187 周期同量级, 且**与等待者数量无关**(296→299, +1%),
   证明等待链位图化改造已彻底消除 O(n) 退化;
2. **残余差距在上下文切换路径**。进一步在 `rtos_sched_context_switch` 内测量:

   开销约 **300 周期** —— 即**约 2/3 花在 PendSV 汇编的保存/恢复上**。

> 口径限制: `swc_ready=64` 含诊断自身开销(链表遍历 + 两次 DWT 读),
> 真实值低于此。切换时刻"最高优先级就绪链长度"实测 avg=1 / max=5,
> 即调度决策本身**不随任务数增长**, 无 O(n) 隐患。

### 0.12 关于"等待链 O(n)"的工作边界(诚实界定)

> **勘误(2026-09-16 复核代码后修正)**: 本节原表述"三条链的 O(n) 插入已全部消除"**不准确**。
> 复核 `rtos_internal_wait_append` 源码后确认: **尾插仍需遍历到链尾, 即入链仍是 O(n)**。
> 真正变化的是 **O(n) 所在的调用路径**: 从"每次释放资源都要执行的唤醒侧"挪到了
> "仅当拿不到资源时才执行的阻塞侧"。且原 `insert_by_prio` 本身也是 O(n),
> 故准确说法是"**O(n) 的重排被去掉、成本被移到低频侧**", 而非"O(n) 被消除"。
> 实测收益(+18.4% → +4.8%)是真实的, 但归因必须按下面的修正表理解。

| 链 | 原实现 | 现实现 | 真实变化 |
|---|---|---|---|
| 就绪链选最高优先级 | 遍历 32 档 | `__builtin_ctz(ready_bitmap)` | ✅ 真 O(n) → O(1) |
| 延时链插入 | 有序插入 O(n) | **表尾缓存 + O(1) 追加快路径**(乱序仍 O(n)) | ✅ 常见路径真 O(1)(有实打实的表尾缓存) |
| 延时链摘除 | 线性搜索 O(n) | 双向 + 表尾缓存交接 | ✅ 真 O(n) → O(1) |
| 信号量/队列等待链**唤醒** | 取链首 O(1)(依赖链已排序) | `ctz(wait_bitmap)` 选优先级 | 唤醒侧本就 O(1); 变化在于**不再依赖链表有序** |
| 信号量/队列等待链**入链** | 有序插入 O(n) | **尾插 O(n)** | ⚠️ **仍是 O(n)**, 仅循环体更轻、且移到低频侧 |

**因此本轮 G2 的准确归因**: 把"维持优先级有序"这一义务从数据结构中删除,
使高频的 give 侧不再为排序买单(排序成本被留在低频的阻塞侧)。
这解释了为何 8 个等待者时退化从 +18.4% 降到 +4.8% ——
剩余 +4.8% 正是**入链侧 O(n) 与唤醒侧分组扫描**的残留(< 原本的排序开销)。
若要彻底消除, 需给每个等待对象加表尾指针(+4B/对象)把尾插也降为 O(1), 见设计文档 L11。

**仍保留的 O(n×m)**, 已评估为**不构成实测瓶颈且不应改动**:

`rtos_internal_mutex_compute_effective_priority()` 在计算优先级继承的
"有效优先级"时, 需要**跨全部注册锁**找最高优先级等待者(外层 ≤ `MAX_MUTEXES`=8,
内层为各锁等待链)。**不能用简单的"每锁一个位图"替代** —— 优先级继承要求的是
**跨锁的全局最大值**, 位图只能给出单锁最大值; 且正确性依赖"跳过所有权已清除的
锁"(释放顺序), 改成位图需额外维护每锁的 OR 聚合状态, **清晰度与正确性风险均上升**。

调用面核实(决定其是否在热路径):

| 调用点 | 触发条件 | 频率 |
|---|---|---|
| `rtos_mutex_take` 提升 | 有等待者进入阻塞 | 仅**争用**时(无争用快路径不经过) |
| `mutex_restore_priority` 释放 | 持有者释放锁 | 仅**争用**时 |
| `rtos_task.c:704` 启动 | 任务启动 | 每任务一次 |

⇒ 该扫描**不在无争用快路径上**。S3(多锁 + 3 生产者/2 消费者)实测队列延迟
avg **15120** / min **2025**, 均优于 FreeRTOS(17707 / 6106), 端到端持平 0.05%,
**无证据表明该路径构成实测差距**。故按"无实测收益的改动不做"原则保留现状,
并把该判断记录于此, 避免后续重复投入。

### 1.2 场景清单

| # | 场景 | 负载形态 | 测什么 |
|---|---|---|---|

## 3. 逐场景分析

### 3.1 S1 优先级反转: FreeRTOS 快 45%(avg) / 2.89×(max)

高优先级任务"发起加锁 → 真正获得锁"的延迟, 背景有一个中优先级任务持续占用 CPU。

- **自研 min 更小**(139 vs 242 cyc, 快 43%): 无竞争时自研的加锁路径更短(专用 mutex 结构, 无队列泛化分支)。
- **自研 avg 慢 84%**(992 vs 540 cyc), **max 慢 2.89×**(17210 vs 5965 cyc): 一旦需要阻塞等待, 自研把等待者**按优先级有序插入**等待链(`rtos_task.c` 的 `rtos_internal_wait_insert_by_prio`, 线性扫描), 且优先级继承提升/恢复时还要 `rtos_internal_requeue_wait_lists` **重排**该链; FreeRTOS 是尾插 + 取首, 依赖"高优先级必然先阻塞"的调度序不变式, 免去排序。
- **最坏情况差距最大**(2.89×)正说明问题在"有竞争时的路径"。这与 S2 的结论互为印证: **自研的加锁路径在无竞争时更快, 在竞争时更慢, 且竞争越激烈差距越大**。

### 3.2 S2 等待者伸缩性: 本报告最重要的发现

| 等待者数 | 自研 give | FreeRTOS give | 自研增量 |
|---|---|---|---|
| 1 | 967 cyc | 474 cyc | — |
| 4 | 1045 cyc | 474 cyc | +78 |
| 8 | 1145 cyc | 474 cyc | +178 |

- **FreeRTOS 完全恒定在 474 cyc**(1/4/8 个等待者逐位相同), 因为 `xSemaphoreGive` → `xTaskRemoveFromEventList` 是 O(1) 双向摘链 + 就绪插入, 与等待者总数无关。
- **自研随等待者数线性增长**: 8 个等待者时 **+18.4%**, 折合 **每个等待者约 +25 周期**。根因是 give 唤醒路径上的 O(n) 操作:
  1. 等待者插入时 `rtos_internal_wait_insert_by_prio` 线性扫描定序(`rtos_task.c:93-113`);
  2. 优先级变化时 `rtos_internal_requeue_wait_lists` 重排;
  3. 唤醒后 `rtos_sched_unblock` → `delay_list_remove`(已是 O(1), 见 P-5 优化)。
  注意 **give 的基数是自研 967 vs FreeRTOS 474(自研慢 2.04×)**, 这一基数差距来自 §3.2 之外的路径差异(专用 sem 结构 + 有序链维护 + 完整临界区), 与既有多份微基准报告的结论一致。
- **定量外推**: 若 32 个任务阻塞在同一信号量上, 按 25 cyc/等待者 计, give 成本将升至约 967 + 31×25 ≈ **1742 周期(10.4µs), 比 FreeRTOS 慢 3.7×**。
- **重要限定**: 这**不是**"自研 RTOS 差", 而是**一个明确的适用边界**。审计报告 (`_audit_test_coverage_gaps.md`) 与 `rtos_design.md:1732` 早已把"等待链/延时链插入 O(n)"列为已知风险并注明"低频路径"; 本报告首次把它**实测定量**。既有 8 项微基准的并发任务数上限只有 4, 因此从未暴露这一退化。
- 设计权衡本身是合理的: 自研保证"任意时刻唤醒的必是最高优先级等待者"(含运行中改优先级的边角场景), FreeRTOS 依赖调度序不变式。**代价是插入成本随等待者数增长**。

### 3.3 S3 混合负载管线: 吞吐持平, 自研队列延迟低 15%, 但控制环偏差 FreeRTOS 完胜

6 个任务(3 生产 + 2 消费 + 1 周期控制)持续运行 9000 条数据:

- **吞吐完全持平**(7899 vs 7895 items/s, 差 0.05%) —— 稳态流水线负载下, 两侧调度/IPC 效率差异被算法工作量淹没。
- **自研队列端到端延迟低 15%**(89 vs 105 µs) —— 与既有微基准结论一致。
- **控制环偏差: FreeRTOS 0/0, 自研 380199/671818 cyc(avg 2.26ms)** —— 这是**本次测试中自研唯一显著劣于 FreeRTOS 的周期性指标**, 且与 S4 的结论**方向相反**。
  - 差异根因: S3 的控制环与 5 个业务任务**共存且负载更重**(生产者以 1ms 粒度让出、消费者做固定工作量)。在这种"重负载 + 多任务就绪"下, 自研的 5ms 控制环出现约 2.26ms 的平均偏差。
  - 与 S4 的对比说明: **自研的周期精度优势只在轻负载下成立**; 重负载下 FreeRTOS 的 tick 路径(内联掩码、无计数、无 isb、O(1) 延时链摘除)更能保住控制环的节拍。
  - 这是本次系统级测试最有价值的发现之一 —— **单模块微基准(S4 式轻负载长跑)无法暴露它**。

### 3.4 S4 周期控制长跑: 自研周期精度高 1.14%

20 秒 / 10000 样本的 2ms 控制环(单任务, 无其它负载):

| 指标 | 自研 | FreeRTOS |
|---|---|---|
| 实际周期 avg | **335983 cyc (1999.99 µs)** | 332186 cyc (1977.3 µs) |
| 唤醒偏差 avg | **0 cyc** | 2 cyc |
| 唤醒偏差 max | **30 cyc (0.18 µs)** | 72 cyc (0.43 µs) |

- **自研的实际周期几乎精确等于 2ms(1999.99µs, 误差 0.0005%)**; FreeRTOS 平均 1977.3µs, **短 1.14%**。
- 两侧唤醒抖动都在亚微秒级, 说明双方都能在 tick 边界准时唤醒; 差异体现在**平均周期**上。
- 与 S3 合起来读: **轻负载下自研周期精度更好, 重负载下 FreeRTOS 抗干扰能力更强**。
- 注: 两侧 `period_actual` 最小值异常偏小(自研 168036、FreeRTOS 494), 经查是**首次采样**的标定伪影(标定结束设了 `prev_cycle`, 而 `delay_until` 首次调用会立即返回), 不是真实提前唤醒; 10000 样本中 1 个伪影不影响 avg/max 结论。

### 3.5 S5 与代码量
- 两者都能在 32KB 堆内建立 8 任务 × 256 字栈的任务集。
- 内核 `.text` 体积几乎相同(自研 21871 B vs FreeRTOS 21372 B, 差 2.3%) —— **"自研更省 Flash"的说法不成立**, 两者同级。

## 4. 测试过程中修正的测量缺陷(方法论留档)

本套件开发中先后发现并修正了 4 处会导致**假结论**的测量/环境问题, 记录在此以避免后续复现时重蹈:

| # | 现象 | 根因 | 修正 |
|---|---|---|---|
| 1 | 场景在创建干扰者后永久停住 | 自研 RTOS 的 `yield()` **仅在相同优先级内轮转**, 独占该优先级时是空操作; 干扰者用 yield 空转即永久霸占 CPU, 且创建者无法恢复 | 干扰者改为按 1ms 粒度让出, 保持"中优先级持续占用 CPU"语义不变 |
| 2 | 周期偏差恒等于一个完整周期 | `nominal` 用 `(ms*1000)/kern_cycles_to_us(1e6)` 计算, 整数除法双重截断(`1e6/168=5952`, 再 `2000/5952=0`) | 改为**运行时标定**: 实测 100 个 tick 的周期数再除以 100 |
| 3 | 上报行被截断 | 两个任务的 `HAL_UART_Transmit` 交错, HAL 串口状态被重入 | `test_log`/`test_report_stats` 整行一次成形, **在临界区内发出** |
| 4 | 标定后场景永久阻塞 | `kern_delay_until(period)` 的单位是 **tick**, 误传了周期数(336000 tick ≈ 5.6 分钟) | 传 tick; 周期数只用于偏差阈值 |

**方法论要点**: 任何"RTOS 计时对比"都必须先回答"我的测量代码本身是否被调度器影响"。本套件最终采用的口径是"相邻两次唤醒的周期计数差", 它对 DWT 回绕安全(25.6s @168MHz, 单次间隔远小于 2^32), 且不依赖任何内核统计接口。

## 6. 结论

1. **系统级负载下, 两套内核的吞吐总体同级** —— 混合流水线吞吐差 0.05%, 代码体积差 2.3%。既有微基准报告中"自研 IPC 快 13%~145%"的优势, 在真实多任务管线里体现为"队列端到端延迟快 15%"。

2. **实测确认了一个架构性退化, 并给出定量边界**: 自研 RTOS 的信号量 give 成本随阻塞等待者数**线性增长**(+25 周期/等待者, 8 个等待者时 +18.4%), 而 FreeRTOS **恒定不变(474 cyc)**。同一根因也解释了 S1 —— **无竞争时自研更快(min 139 vs 242 cyc), 有竞争时更慢(avg 慢 84%、max 慢 2.89×)**。**32 个并发等待者时预计慢 3.7×**。

3. **该退化的适用边界**: 只有"**大量任务阻塞在同一同步对象上**"才会命中。典型嵌入式负载(每对象几个等待者)不受影响 —— S3 的 6 任务管线吞吐与 FreeRTOS 持平即为证。若目标应用是"几十个任务抢同一把锁/信号量"的形态, 必须纳入评估。

4. **周期行为出现"负载相关的交叉", 这是微基准测不出来的**:
   - **轻负载**(S4, 单任务 2ms 环): 自研更准 —— 实际周期 1999.99µs vs FreeRTOS 1977.3µs, 自研准 1.14%; 抖动也更小(avg 0 / max 30 vs avg 2 / max 72 cyc)。
   - **重负载**(S3, 6 任务共存): **FreeRTOS 完胜** —— 控制环偏差 0/0 vs 自研 380199/671818 cyc(平均偏差 2.26ms)。
   - 结论: **自研的周期精度优势只在低负载下成立**; 一旦系统有其它就绪任务竞争 CPU, FreeRTOS 的 tick 路径(内联掩码、无计数、无 isb、O(1) 延时链摘除)更能保住控制环节拍。**单模块微基准(即既有报告的做法)无法发现这一点。**

5. **确定优势两处**: ① IPC 端到端延迟(队列快 15%); ② 轻负载下的周期绝对精度(准 1.14%)。

#### A.2.1 发现并修复的缺陷: `rtos_task_create` 栈尺寸上界不可达

**现象**(串口):
```
BT|GEOM|sizeof_tcb=140|heap=32768|stack_max_words=8157
BT|TASK|create_stack_upper_ok|FAIL|actual=-2|expect=0     ← -2 = RTOS_ERR_NO_MEM
```

**分析**(结合 .map): `nm` 与 map 显示内核堆为单个 0x8000 字节 `.bss.s_heap_buf`
(`0x200015E8`, rtos_heap.o), `RTOS_CONFIG_HEAP_SIZE` = 32768。而
`rtos_task_create` 的上界校验写作:

```c
stack_size > (RTOS_CONFIG_HEAP_SIZE / sizeof(rtos_stack_t))   /* = 8192 字 = 整个堆 */
```

该式**两处高估**, 使 API 声明可接受、实际必然失败的"假上界":

1. **未扣 TCB**: TCB 在栈之前从同一个堆分配, 已占 `sizeof(rtos_tcb_t)` = 140 字节;
2. **未计分配器开销**: 每次分配额外吃掉一个 8 字节块头, 且请求向上对齐 8 字节。

仅修正第 1 点后上界变为 8157 字, **仍然失败** —— 说明必须把分配器口径一并纳入。

**修复**:
- 新增 `rtos_heap_get_max_alloc()`: 返回**当前最大单块连续空闲块**可供用户使用的
  字节数(已扣该块块头并对齐 8 字节)。
  刻意**不**用 `s_heap_free` 求和 —— first-fit 只在一个连续块内满足请求,
  碎片化时空闲总和远大于任何单块, 用总和会让"参数校验"错误地放行本该
  以 `ERR_NO_MEM` 失败的请求(实测: 求和口径下 `create_stack_upper_ok`
  时而通过时而失败, 即该高估的直接证据)。
- `rtos_task_create` 改用 `stack_size * sizeof(rtos_stack_t) > rtos_heap_get_max_alloc()`
  作为上界判据, 与分配器口径完全一致。
- 增加编译期兜底 `_Static_assert(sizeof(rtos_tcb_t) < RTOS_CONFIG_HEAP_SIZE, ...)`。

**修复后实测**: `create_stack_upper_ok` PASS(恰好上界可创建),
`create_stack_over_heap` PASS(超过整堆必然由参数校验拒绝, 返回 `ERR_PARAM`)。

**回归**: 修改 `rtos_task.c` / `rtos_heap.c` 后全量自测
`ST|SUMMARY|pass=391 fail=0 info=11 total=402|END` ✅
