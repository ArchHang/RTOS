# 运行正确性监督：设计提案

**状态：方案讨论，尚未实现，也没有对应的新硬件验收结果。**
本次已交付的是共享通道与有界诊断记录器。本提案整理后续如何发现“CPU 仍在运行，
业务已经失效”的问题，不新增配置宏、公共 API、健康任务或看门狗行为。

## 问题与已有能力的边界

当前记录器保存 WAIT、WAKE、RUN、RETURN，并在触发冻结后解释有限历史。
它不会自动判定 DMA 中断漏服务、旧帧被重复处理或算法结果错误，也不保证任意久以前的
等待起点仍在环中。检测和留证需要分别设计，不能把“有 trace”当作“已有自动健康监督”。

BASEPRI 残留是一个具体例子：它影响 CPU 对中断的响应，DMA 控制器可能已经完成搬运。
按本工程的低优先级 SysTick/PendSV 配置，长期残留的 `0x50` 还可能使内核 tick 和调度
停止，普通监控任务也无法执行。更正后的机理与原始复现范围见
[BASEPRI 修复报告](rtos_basepri_fix_20261025.md)。

## 第一层：内核恢复契约

在承诺保持屏蔽状态的配对调用边界，检查 BASEPRI、PRIMASK 和嵌套计数是否恢复到
进入前的值。只有明确承诺“当前未持有任何屏蔽”的线程检查点，才要求相应值为零。
高优先级 ISR 抢占正常临界区时观察到非零 BASEPRI，不应单凭该读数报警。

预期值应有独立依据，例如调用者栈上的诊断副本；不能把“实际恢复值”和“期望值”
都取自可能已经被污染的同一个全局 saved_mask。检查须放在事务完成的稳定边界，
避免把进出临界区的合法中间状态误判为不一致。

另外设置经过预算的最长屏蔽时间。长操作、调度挂起和应用主动加强屏蔽需要明确契约；
不能将一次非零采样直接解释成永久泄漏。该机制需单独测量常开开销。

## 第二层：业务进展、期限与顺序

建议由应用登记有限数量的监督实体，每个实体声明业务编号、状态转换、截止时间和
数据有效性约束。以下采集链是示例，不是已定义的 API：

```mermaid
flowchart LR
    A[提交采集 / 事务编号] --> B[硬件完成]
    B --> C[ISR 服务]
    C --> D[投递成功]
    D --> E[消费者取得新数据]
    E --> F[校验与处理完成]
```

例如每 10 ms 一块数据、最多容忍 30 ms 没有新的有效块。这些数值只是说明方式，
实际期限和容忍次数必须由业务定义，并区分正常运行、空闲、停机和维护模式。

| 观察组合 | 可以报告的异常 | 后续核对 |
|---|---|---|
| 提交后超过完成期限，硬件未完成 | 传输/触发阶段超期 | 外设状态、总线和错误标志 |
| 硬件完成、IRQ enabled/pending，ISR 长期不前进 | 中断响应阶段超期 | BASEPRI/PRIMASK、优先级、其他 ISR 占用 |
| ISR 前进但投递没有成功 | 驱动到 IPC 的交接失败 | 实际返回值、背压和对象生命周期 |
| 投递成功但消费没有完成 | 消费阶段超期 | 任务就绪/阻塞状态、资源和优先级 |
| 持续上报但编号/代次未更新 | 重复或过期数据 | 数据年龄、缓冲归属及消息身份 |

pending 或完成标志不是单独确定根因的证据。循环 DMA 的标志可能合并多个事件，
不能每次轮询到同一完成位就累计为一帧，也不能只靠 NDTR 还原任意次数的绕圈。
应结合数据中的序号、可核对的事务身份及配置的节拍判断；采样尽量不清除驱动拥有的标志。

监督点应表示“新事务完成了某阶段”，而不是“线程又执行了一次循环”。应用仍需定义
正确性：CRC 可覆盖部分数据损坏，范围、变化率、守恒关系或独立冗余结果才能覆盖更多
业务错误。RTOS 无法自行知道一份推理结果或控制指令是否符合真实世界。

## 第三层：独立观察与硬件兜底

普通线程监督以外，还需要可选的独立时基和高优先级探针。其职责应限制为固定数量的
原生字读取、超期判定和首故障发布；不得调用正常 RTOS API、分配、打印或等待被打断的
写者。当前 `rtos_diag_fault_freeze` 仅适用于最终停机的故障处理，不能直接用于会返回的
周期探针，也不能由 NMI 调用。

探针应使用单独的应急发布协议。中断号要区分探针自身与被打断上下文，不能把探针内
读取的 IPSR 当作被打断任务的身份；不能无检查地追踪 TCB、对象或损坏的栈。

PRIMASK 仍能屏蔽普通高优先级中断，因此需要 IWDG 等独立硬件兜底。喂狗由监督结果
决定，只有当前模式下必要业务的进展、新鲜度、顺序和期限全部满足才允许刷新。
idle、某个正常任务或周期 ISR 无条件喂狗，会掩盖其他业务失效。

调试暂停、低功耗和时钟变化必须有明确策略。硬件看门狗的调试冻结配置也要纳入测试。
监督者完全不能执行时，可能只能得到看门狗复位原因，不能保证留有完整的软件快照。
跨复位证据需要另外设计保留区、提交标志、校验和及启动读取；当前 BSS 环形记录不会
自动跨复位或掉电保存。

发现异常后由应用选择安全输出、停止新业务、留证及受控复位。不能用自动清零 BASEPRI
或强制归还仍被访问的共享块代替恢复协议。

## 可移植性、算法与配置方向

| 边界 | 拟承担职责 |
|---|---|
| 可移植监督核心 | 监督实体、业务编号/代次、检查点顺序、期限和状态汇总 |
| port/BSP | 独立时间、屏蔽状态、IRQ/外设采样、看门狗刷新与保留区 |
| 应用 | 哪些业务必须前进、什么数据有效、允许的空闲和安全动作 |
| 现有诊断服务 | 合法上下文中的事件留证和等待解释 |

内存规模应在配置期有界；活跃监督实体不能被 LRU 淘汰。容量满时必须明确拒绝登记，
不能静默漏监。小规模可使用固定数组和表驱动状态机；较大规模再依据测量选择有界索引
及截止期结构，不预设哈希平均复杂度就等于最坏实时保证。

轻量监督应与完整 trace 分开配置。后续可以在 Release 保留必要的业务检查和首故障槽，
在 Debug 开启详细轨迹；其成本必须单独上板测量，不能沿用已有 trace 的开销或宣称零成本。

## 实现前必须明确的验收条件

| 正/负对照 | 预期判据 |
|---|---|
| 高 IRQ 抢占合法临界区、读到非零 BASEPRI | 不误报恢复错误 |
| 返回后屏蔽不匹配，或超过已声明的屏蔽预算 | 稳定发现并保留首个异常 |
| 单独禁用 DMA IRQ | 业务期限和中断链路监督发现 |
| 停止消费者、制造投递失败、重复旧数据 | 分别报告对应阶段，不用相同心跳掩盖 |
| 屏蔽 SysTick | 独立时间和探针仍可发现进度停滞 |
| PRIMASK 长期置位 | 硬件兜底生效，并如实说明软件留证边界 |
| 空闲/低功耗/维护模式、调试暂停 | 不产生无依据的业务超期 |
| 容量耗尽、计数回绕、重建及旧检查点迟到 | 显式失败或按代次拒绝，不串用旧健康状态 |

上述测试尚未针对新监督模块执行。下一步实现应先确定合同和失效处理，再开发和测量。
