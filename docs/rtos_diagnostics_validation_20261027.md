# 有界故障记录与等待解释：研发与实板验证报告

日期：2026-10-27。平台：NUCLEO-F446RE、168 MHz、1 kHz tick、GCC 11.3、
ST-LINK SWD，USART2 COM3 / 115200 8N1。最终汇总为
[`final_summary.json`](../hil/diagnostics_20261027/final_summary.json)。

本轮完成了可编译裁剪的诊断服务，并在真实 F446 上验证正常等待、复杂并发及致命故障。
最终代码完成 **35 份烧录捕获**：34 份正常运行、1 份预期 UDF 停机；另外完成了恢复日常
构建后的烧录与启动检查。早期联调、旧代码布局和被拒绝的捕获单独保留，不计入这些通过数。

## 交付行为

| 项目 | 当前实现 |
|---|---|
| 编译开关 | `RTOS_CONFIG_USE_DIAGNOSTICS`，默认 0；Debug 按需开启，Release 编译关闭 |
| 容量 | `RTOS_CONFIG_DIAGNOSTIC_CAPACITY`，默认 64，允许 8..1024 的 2 次幂 |
| 事件 | WAIT、WAKE、RUN、RETURN，以及创建、挂起、恢复、删除和应用 marker |
| 等待解释 | 区分资源唤醒、通道重试通知、延时到期、超时、对象销毁、关闭及任务取消 |
| 故障记录 | 保留故障前已提交事件；CPU 故障入口无锁冻结，原 `g_fault` 继续保存寄存器 |
| 缺失历史 | 明确返回 UNKNOWN/INCOMPLETE，不解引用旧地址，不猜测原因 |
| 可移植边界 | 标准 C 记录算法 + 现有内核/port 接口；不使用 DMA，不增加 TCB 字段 |

公共接口是 `rtos_diag.h`，实现为 `Services/rtos_diag.c`，私有观察点在
`rtos_diag_internal.h`。内核在已有保护域内写入固定记录，冻结后逐条读取和分析。
重置通过不回绕的序号逻辑失效旧数据，O(1) 完成，不在临界区清空整个缓冲。
详细协议、图示与使用方式见[诊断设计](rtos_diagnostics_design.md)。

“资源唤醒”和“API 成功”分别保留。例如真实测试中，通道接收者先被 OK 通知唤醒，
因高优先级线程持续占用 CPU，恢复时总预算耗尽：记录为通知原因、`wake_result=0`、
`return_result=-3`。同址关闭重建也能保留“原唤醒为 CLOSED，最终返回为 DELETED”的区别。

## 开发中发现与修正

| 问题 | 修正方案 | 验证 |
|---|---|---|
| 原 CPU 故障报告把 `SP-base` 当作已用栈 | 对向下生长栈计算 `capacity-(SP-base)`，增加栈范围检查，明确当前帧而非历史峰值 | 实际 UDF：容量 4096、剩余 4056、已用 40 字节；SWD 与 UART 一致 |
| 初版诊断仅按 `blocked_on` 判断挂起取消，遗漏纯延时 | 观察原 DELAYED/BLOCKED 状态；诊断取消原因独立于原 API 返回值 | 有限 150 tick 和 FOREVER 延时挂起/恢复，以及资源唤醒后再挂起 |
| 已返回的等待被后续自挂起覆盖成“仍挂起” | RETURNED/DELETED 是 episode 终态；下一次 WAIT 才开始新 episode | 宿主终态回归、实板 worker 返回后停驻 |
| 序号耗尽后若故障覆盖冻结原因，可能错误重新启用 | 增加独立耗尽锁存，序号/任务身份永不复用；只停止诊断采集 | 宿主逼近 UINT32_MAX、故障和重置交错 |
| 查询记录局部值触发 O3 严格编译告警 | 初始化冷路径局部记录，保持错误输出不变契约 | 最终 454 项严格编译全通过 |
| 测试清理重复关闭已关闭通道，被误判为失败 | 夹具跟踪预期关闭状态，检查完整资源守恒后按状态清理 | 首轮 471/472 的原始失败保留；修正后最终矩阵全部通过 |
| 故障接受器把启动菜单的 UNDEFINSTR 算入解码 | 只接受故障状态段内的解码，并要求实际 CFSR；补“只有菜单”的负例 | 48 种损坏输入拒绝；32 个旧普通捕获经新旧接受器双重复核 |

上述诊断解释和夹具问题属于本次开发过程中发现的缺口；本轮未把它们包装成原有调度
或 IPC 算法的缺陷。既有资源分配、返回优先级、TCB、PendSV 栈帧及中断屏蔽协议保持原语义。

## 正常路径与边界覆盖

最终捕获位于 [`evidence/final/`](../hil/diagnostics_20261027/evidence/final/)。
每次先开串口、再烧录和读回校验，保存原始 UART、构建详情、配置、输入身份与结束条件。
实际探针及烧录成功标记均由接受器核对，不以模拟串口或 SUMMARY 单行代替实板证据。

| 验证组 | 最终覆盖与结果 |
|---|---|
| 新功能矩阵 | BASEPRI/PRIMASK × 断言 ON/OFF × O0/O2/O3，12 个镜像，每个 472 项，共 5664 项通过 |
| 最小容量 | 8 槽，两种屏蔽配置，各 52 项通过；覆盖覆盖旧数据、会话失效与真实 IRQ |
| 功能关闭 | 11 项通过；全部 API 返回 DISABLED，输出不变 |
| 等工作量基准 | O2/O3 × ON/OFF，4 个镜像、72 条原始计时、288 项契约通过 |
| 宿主模型 | 8 个进程、1,109,772 项检查；O0/O3 × 容量 8/64/1024，并含 OFF 分支 |
| 严格编译 | 18 个自研单元的 432 组合、18 项 M7 代码生成、4 项 C11/C++17 头探针，共 454/454 |
| 配置边界 | 10 项真实 ARM 编译：合法容量通过、非法容量准确拒绝、OFF 分支无状态 |
| 记录接受器 | 3 个正例与 48 个损坏输入通过预期判据 |
| SWD 接受器 | 真实正例与 10 个损坏状态/指令/身份输入通过预期判据 |

实板新夹具使用真实任务、SysTick、PendSV 和优先级 0/4/5 的 TIM7 IRQ。
覆盖 9 类等待操作，包括事件 ANY/ALL 两条路径；检查 WAITING、唤醒后尚未运行的 READY、
上下文提交和实际 RETURN。另覆盖事件部分 bits 非零但超时、对象 deinit、挂起、恢复、
删除、通道关闭/同址重建、通知后迟到超时，以及起点被覆盖或等待期间重置后的 UNKNOWN。
高优先级 IRQ 的诊断 API 违约在关闭断言后仍被拒绝，屏蔽值和嵌套状态得到保留。

宿主直接测试生产 C，并用独立 FIFO 模型验证保存与覆盖。计数耗尽、记录缺口、并发
读取重置和三个写入阶段的终止故障采用明确的白盒注入；它们不是 ARM 中断仿真。
本机没有使用 ASan/UBSan，不声称覆盖了对应的检测能力。

最终 13 组集成回归在诊断和共享通道同时启用的配置下通过，包括：

- audit 117、selftest 432（另有 10 INFO）、boundary 103；底层上下文 24 与优先级 22 项；
- 互斥锁继承 910、混合等待 1600、对象销毁窗口 80、互斥锁边界 87、最大注册图 259 项；
- BASEPRI/PRIMASK 分别 622/620 项，均包含完整 600 单元抢占矩阵；
- 16 优先级业务流水线连续 30 秒，165 项通过，worker_errors=0。

业务流水线的六个来源合计 **65926 条成功接纳消息全部验证，pending=0**。
两路 syscall IRQ 分别进入 30068/43128 次；高优先级 IRQ 进入 557435 次，观测到
30307 次嵌套和 732 次三层交错，错误与恢复不匹配均为 0。堆的空闲量和最大块在测试前后
相同，资源归还与中断清理契约通过。被容量策略明确拒绝的消息单独计数，不当作成功接纳消息丢失。

这些结果证明所列条件下未观察到回归；30 秒合成业务和单块诊断场景不等同于长期现场
业务认证。本轮没有外接传感器或 USB 数据总线测试，SWD/串口连接也不构成 USB 功能证明。

## 实际致命故障与 SRAM 复核

[`fault_final`](../hil/diagnostics_20261027/evidence/final/fault_final/) 在记录 marker、
完成两 tick 延时、再写 marker 后执行真实 UDF。随后使用同一烧录 ELF，以 Attach 模式
连接 SWD，不复位目标；原始调试命令和数据位于
[`fault_debug/20261027_165907_9971/`](../hil/diagnostics_20261027/fault_debug/20261027_165907_9971/)。

实际读取结果：`frozen=1`、`fault_valid=1`、`writing=0`、`CFSR=0x10000`；
当前会话保留 **9 条连续提交记录**，两条 marker 的原始值和 detail 完整。
故障任务的事件为 `MARK → WAIT → WAKE → RUN → RETURN → MARK`，延时确已到期。
UART 与 SRAM 的 PC 相同，直接读取该目标地址的半字为 `0xDE00`，反汇编为 `udf #0`。
因此这里的冻结结论来自实际 RAM 和目标指令读取，不只来自 UART 提示。

致命故障入口不使用正常内核临界区，不读取可能失效的 TCB/对象，也不清理业务资源。
它只适用于最终停机；故障后返回正常写者、NMI 共用入口、掉电持久化与跨复位恢复均未实现。

## 性能与资源成果

以下为三次等工作量样本的中位数，单位为 **cycles/完整交换**。每次样本 1024 次交换，
校验和一致且错误为 0，包含 API、循环、真实调度和 SysTick 干扰。

| O2 路径 | 关闭 | 开启 | 耗时增加 |
|---|---:|---:|---:|
| 信号量阻塞交换 | 1420.61 | 2308.12 | 62.47% |
| 队列阻塞交换 | 1806.12 | 2639.42 | 46.14% |
| 通知阻塞交换 | 1364.82 | 2332.03 | 70.87% |

O3 的对应耗时增加 52.61%–71.16%。非阻塞控制路径的 O2 变化为 +2.78%、-1.27%、
+3.52%；代码布局也会影响未写记录的路径。全部三轮样本、min/median/max 和链接资源
保存在[最终性能分析](../hil/diagnostics_20261027/performance_analysis/20261027_165203_421154/report.md)。
这些值不是单条记录成本、整机吞吐下降比例或 WCET。

完整默认模块的静态预算为 **2604 字节**。基准和日常工程经链接裁剪后，开启净增加
2596 字节 RAM；日常开启的 `data+bss=128676`，关闭时为 126080 字节。
本工程不能仅凭模块容量允许 1024 就假定日常应用还能容纳该配置。
最终 O2 查询调用链的已知栈成本约 304 字节，O0 为 376 字节，还需叠加任务业务、
格式化输出与异常现场；建议诊断维护任务从 1 KiB 起配并验证实际水印。

**记录会显著扰动高频任务交换，因此默认关闭是本轮交付的重要部分。**
关闭且断言关闭、O2/CHANNEL=1 时，修改前后原有 **17/17 单元**的全部可装载节内容、
尺寸、对齐和重定位目标一致；新增 OFF 模块没有静态状态。
断言开启会因源码插入而改变 `__LINE__` 常量，所以未宣称整个旧 ELF 完全相同。
日常 OFF 镜像的符号表确认没有诊断函数、RETURN helper 或记录缓冲。

编译开启后再 freeze 仍有调用成本，发布时应真正编译关闭。配置示例：

```c
/* Debug 定位问题时设为 1；Release 设为 0，并完整重编译。 */
#define RTOS_CONFIG_USE_DIAGNOSTICS (0)
#define RTOS_CONFIG_DIAGNOSTIC_CAPACITY (64U)
```

## 使用边界与最终工程状态

有限历史的窗口约为“槽数 / 每秒事件数”。64 槽在 10000 events/s 下约保留 6.4 ms，
长时间等待的起点可能已经覆盖；本轮没有额外为每个 TCB 保存永久等待信息。
UNKNOWN/INCOMPLETE 是这类情况的正确结果。查询结果描述最近记录到的等待 episode，
不能仅据地址判断对象代次、实时锁拥有者、循环死锁或业务数据完整性。
故障也可能发生在内核修改状态与观察点之间，历史前缀不能替代对故障 PC 和内核状态的核对。

事件序号耗尽后停止诊断采集并拒绝重新启用；**RTOS 仍继续运行**。
会话号耗尽时拒绝新的 reset、保留现有会话，不回绕或复用身份。
任务身份即将复用时也永久冻结诊断，不改变原任务 ID 分配和调度行为。

最终已恢复所有权威日常构建模板、移除 HIL 副本及变体 stamp，并重新烧录默认关闭的
日常固件；串口确认 task 0/1 在恢复启动后运行。恢复后的可装载镜像与已验证的 daily OFF
镜像相同，`main.c` 内容与任务开始前相同。保留了此前共享通道修改；上述为硬件验收完成时的状态，
随后源码、测试和文档的 Git 发布范围见[本次交付报告](rtos_release_20261027.md)。
源码为 18 个自研 RTOS 单元、工程为 59 个单元；设计手册、源码导览与 HIL 说明已同步更新。

复现命令和完整验证边界见[批次说明](../hil/diagnostics_20261027/README.md)。
